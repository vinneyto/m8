# Поздравительная открытка на 8-е марта

Репозиторий состоит из двух частей:

- фронтенд в корне проекта (`/`) на React + Vite + react-three-fiber;
- API в папке `api/` на NestJS.

На текущий момент фронтенд показывает текст из query-параметра `?text=...`, а API уже умеет:

- создать открытку (`POST /cards`);
- получить открытку по id (`GET /cards/:id`).

Фронтенд пока не интегрирован с этим API.

## Что изменено в этой ревизии

- проект переведен с `bun`-скриптов на обычный `npm`;
- обновлены зависимости до актуальных совместимых версий;
- фронтенд больше не привязан жестко к GitHub Pages-пути `/m8/`;
- API переведен с `bun:sqlite` на `node:sqlite`, чтобы запускаться на обычном Node.js;
- добавлена базовая настройка CORS для API.

## Требования

- Node.js 22+
- npm 10+

## Локальный запуск

### Фронтенд

```sh
npm install
npm run dev
```

По умолчанию приложение откроет открытку с текстом по умолчанию.  
Для передачи своего текста можно использовать query-параметр:

```text
/?text=<base64>
```

### API

```sh
cd api
npm install
npm run start:dev
```

По умолчанию API поднимается на `http://localhost:3000`.

### Переменные окружения API

- `PORT` - порт приложения, по умолчанию `3000`
- `CORS_ORIGIN` - список origin через запятую; если не задан, CORS открыт для всех origin
- `CARDS_DB_PATH` - путь к SQLite-файлу, по умолчанию `cards.sqlite`

## Развертывание на Vercel

### Что можно задеплоить уже сейчас

Фронтенд можно деплоить на Vercel сразу:

1. Import Project из Git-репозитория.
2. Root Directory: `/`
3. Framework Preset: `Vite`
4. Build Command: `npm run build`
5. Output Directory: `dist`
6. Install Command: `npm install`

После этого фронтенд будет собираться как обычный статический Vite-проект.

### Что важно про текущий API

Текущий API в `api/` **не готов к Vercel как production backend в текущем виде**, потому что:

- это long-running NestJS server, а не Vercel Function;
- он хранит данные в локальном SQLite-файле;
- локальная файловая система на Vercel эфемерная и не подходит для постоянного хранения открыток.

Иными словами:

- **локально** текущий API подходит;
- **на Vercel** storage для текстов нужно вынести во внешний managed storage, а сам backend - либо в Vercel Functions, либо в другой хостинг.

### Что есть у Vercel для хранения текстов

#### 1. Vercel KV

Подходит, если нужен очень простой сценарий:

- сохранить текст по `id`;
- получить текст по `id`;
- вести отдельный счетчик по месяцам.

Пример ключей:

- `card:{id}` -> текст открытки
- `cards:count:2026-03` -> количество созданных открыток за месяц

Плюсы:

- очень просто стартовать;
- хороший выбор для create/get по id;
- отлично подходит для serverless-функций.

Минусы:

- сложнее делать выборки, аналитику и админские операции;
- структура данных быстро становится "ручной".

#### 2. Vercel Postgres

Лучший вариант, если хочешь нормальный backend с ростом функциональности.

Подходит для:

- таблицы `cards`;
- поля `id`, `text`, `created_at`;
- SQL-запросов;
- лимитов, статистики, выборок и будущей админки.

Плюсы:

- модель данных почти один в один повторяет текущий SQLite;
- проще масштабировать логику;
- удобнее для отчетов и поддержки.

Минусы:

- чуть больше инфраструктурной настройки, чем у KV.

**Практическая рекомендация:** если backend нужен "всерьез", выбирай **Vercel Postgres**.  
Если нужен максимально быстрый MVP только для `create/get`, можно стартовать с **Vercel KV**.

#### 3. Vercel Blob

Подходит для файлов и больших объектов.  
Для хранения коротких текстов открыток как основной базы данных - **не рекомендуется**.

#### 4. Edge Config

Подходит для конфигов и фичефлагов, но **не для пользовательских открыток**.

## Рекомендованный путь для этого проекта

Для Vercel я бы выбрал такую схему:

1. Оставить фронтенд как Vite static app.
2. Перенести backend-эндпоинты в Vercel Functions.
3. Для хранения текстов использовать:
   - **Vercel Postgres** - если нужен нормальный SQL backend;
   - **Vercel KV** - если нужен очень быстрый MVP.
4. После этого изменить фронтенд:
   - вместо `?text=` создавать открытку через API;
   - открывать открытку по id или slug.

## Что еще нужно учесть перед production
